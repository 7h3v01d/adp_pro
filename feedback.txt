🔴 RC blocker 1 — terminal downloads resurrect on restart
This is the biggest thing I found.
save_downloads() correctly persists terminal states:
COMPLETED
STOPPED
ERROR
But load_downloads() doesn't restore those statuses.
At download_panel.py:534–555, every record goes through:
self.add_download(... start_immediately=False)
And add_download() does:
self.download_queue.append(manager)
for unscheduled downloads.
A newly constructed manager begins as:
Status.PENDING
Only PAUSED gets corrected afterward.
Then:
self.process_queue()
runs.
So this:
STOPPED
   ↓ restart
PENDING
   ↓
starts again
And:
COMPLETED
   ↓ restart
PENDING
   ↓
potentially downloads again
For a stopped download this is particularly unequivocal because stop() deletes its progress sidecar.
That's a semantic violation:
Stop means stop, including across restart.
Tests you need
test_completed_session_restores_completed_without_network
test_stopped_session_stays_stopped
test_error_session_stays_error
I'd make those mandatory before final.

🔴 RC blocker 2 — Retry can defeat your new path reservation
This is a beautiful second-order bug.
You fixed:
PENDING A → output.iso
PENDING B → output.iso
because A reserves the destination.
But terminal jobs intentionally release their reservation.
So:
A COMPLETED → output.iso

B added → output.iso
B now owns/reserves path

user clicks Retry on A
retry_selected_download() does:
manager.prepare_retry()
self.download_queue.append(manager)
There is no new path-conflict check.
Now both A and B target the same destination.
REST/MCP retry has the same problem in api/controller.py:145–155.
Fix
Make reservation checking reusable:
_find_path_conflict(save_path, exclude_download_id=None)
and validate before any terminal job transitions back into PENDING.
Adding a job and resurrecting a job should obey the same ownership rule.

🟠 The deeper issue: slots don't have owners
This is probably the most valuable architectural observation from this audit.
Currently you have:
self.active_downloads = 0
But you don't know which managers own those slots.
That has become dangerous now that PAUSED has two meanings.
Runtime pause
download acquired slot
→ PAUSED
→ still owns slot
Restored pause
application starts
→ restored as PAUSED
→ never acquired a slot
You correctly special-cased GUI resume using metadata_initialized.
But stop/remove still do:
if status in [DOWNLOADING, PAUSED, STARTING]:
    ...
    finish_download_slot()
So imagine:
A = running, owns the only slot
active_downloads = 1

B = restored PAUSED
owns no slot

user removes B
        ↓
finish_download_slot(B)
        ↓
active_downloads = 0
A is still running.
The queue can now start C.
Your concurrency invariant is broken.
API has another manifestation
AppController._resume_download_impl() still does:
manager.resume()
directly.
So REST/MCP completely bypasses the careful restored-pause queue logic you just added to the GUI.
I would fix the model, not the symptoms
Something like:
self._slot_holders: set[str] = set()
Then:
acquire(download_id)
release(download_id)
are idempotent.
And:
active_downloads = len(_slot_holders)
Suddenly all of these become much harder to get wrong:
•	completion 
•	error 
•	stop 
•	remove 
•	restored pause 
•	API resume 
•	retries 
•	double callbacks 
This would be a very good refactor.
Also, make the controller call panel-level lifecycle methods rather than calling DownloadManager.resume()/pause()/stop() directly. The panel now owns concurrency policy; the API should not circumvent it.

🟡 The stale-worker race remains
The worker correctly checks epoch before processing a chunk:
if self._is_stale():
    return
But then it can block here:
self.speed_limiter.acquire(len(chunk))
During that wait:
worker valid
→ rate limiter sleeps
→ user presses Stop/Pause
→ epoch changes
→ limiter returns
→ worker writes chunk
There is no second staleness check before:
f.write(chunk)
Small window, real race.
I'd add:
self.speed_limiter.acquire(len(chunk))

if self._is_stale():
    return

f.write(chunk)
Eventually I'd also epoch-tag chunk_downloaded, as you've already done for finished/error signals.
